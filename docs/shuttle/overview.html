Design overview · companion to docs/shuttle/spec.md v0.3 and plan.md v0.3

Shuttle, Drawn

Routes that notice a file or a message, carry it to where it belongs, stamp the source, and tell the systems that care. The whole design exists to make one sentence true: an item can be lost only if the source, the target and the Oracle state store all lose it at once.

Part 1

The job, as a courier route

A shuttle runs routes. On every route a courier does the same six things for each item, and writes every one of them into a logbook before doing the next.

1 · noticea folder is checked every hour, or a message arrives
2 · pick upthe bytes come to a local workbench
3 · work on itcheck, rename, zip, read the label, split a manifest
4 · dropa MinIO bucket, or another SFTP server
5 · stamp the sourcemove, delete, or acknowledge · the commit
6 · tell peopleat pickup, at drop, or at the stamp · or nobody

The three promises

Nothing is lost

The source is stamped only after the copy is verified at the target. A crash before the stamp leaves the item where it was, to be redone.

Nobody is told too early

Every tell is written into the logbook in the same stroke as the step it announces, and a separate loop sends it. It can never be sent about something that did not happen.

One bad item never stops the rest

Every item is handled on its own. An item that fails five times, or fails a check, is marked, left in place, and handed to an operator. Nothing is deleted except by a configured stamp; at the target the application only ever overwrites, and older copies expire by the bucket's own rule.

Part 2

The whole system in one picture

The framework, not a deployment. Object stores and channels are declared once, and a route gives each a role where it uses it: a store is polled, fetched from or stored into; a channel is subscribed to or notified. Every route is its own supervised loop; all routes share the state store, the stores' session pools and one notifier. Routes and the notifier never talk to each other except through the state store and one wake signal.

One item's journey, and the states it leaves behind

One coroutine per source object, bounded per route. The ack is the commit point for the source. A notification is an outbox row written in the same transaction as the state it announces, which is what the row's on_state records.

Where a value travels: from a file name to a body

Attributes are the only way information leaves a processor, and they are checked twice: at boot against the declarations, and at attribute freeze against every mapping table the route notifies, before anything is stored.

The state store, as it looks for one item

file_transfer id 4471 vendor-drop /inbox/12345-ACME.csv 9,812,404 B md5 3f9c…e2a1 attributes {orderNumber: 12345, vendor: ACME} SEEN → FETCHED → PROCESSED → STORED (landing/ACME/12345/20260903-12345-ACME.zip, v 7Kq…) → ACKED → DONE delivery_outbox for 4471 on_state ACKED downstream DELIVERED attempts 1 reference req-8c21f on_state FETCHED upstream-receipt PENDING attempts 3 next 07:53:40 last HTTP 503

Two tables because one item has many notifications, each with its own attempts, retry time and reference. on_state is the moment a row announces and never changes; notification_state is the row's own progress. No attempt-history table: every attempt logs its transfer id, moment, channel, attempt, status and reference.

The second loop: the notifier

Pending rows become channel calls through a cold Flow with a bounded buffer and parallel workers; emit suspends when the buffer is full, so the next select runs only after the previous batch drained. Delivered rows record the receiver's reference and flip the transfer to DONE when every row is delivered; retryable outcomes back off with jitter; rejected or exhausted rows become FAILED without touching the transfer. Every transaction that creates rows wakes the loop; a sweep every 30 s catches the rest. Cancelling leaves rows PENDING. The in-memory set of in-flight ids is bounded by batch plus workers, empty when idle, and must not survive a restart.

Part 4

The five decisions that carry the requirements

Ranked. The spec's decision log has thirty-five entries; these are the ones the promises rest on.

1

One durable state store is the only truth; the two in-memory sets never survive a restart.

Carries "nothing is lost": every item has a known resume point, and after a crash the next trigger continues from it. The connector's own dedup store is deliberately unused, and the notifier's id set is a guard, not a store.

spec D1 · D7 · 4.3 · 4.4 · I8
2

Ack is the commit; a notification is an outbox row written in the transaction of the state it announces.

Carries "nobody is told too early": a tell is exactly as durable as the step it reports, and a separate loop sends it at-least-once. The row's on_state is the moment, its notification_state the progress.

spec D6 · D26 · I11 · I20
3

Object stores and channels declared once, role given at the route; a target promises "the current copy is the one just written" and never deletes.

Carries reuse without duplicated secrets, and retries that overwrite instead of creating siblings. Expiry of older versions belongs to the bucket's lifecycle rule, so no transfer can erase what an earlier one delivered, and the process holds no delete permission.

spec D21 · D22 · D5 · I6
4

One Processor seam, pure over staging, with attributes as its only output.

Carries any processing that is safe to re-run after a crash, and values that are checked against every mapping before anything is stored.

spec D23 · D24 · D25 · I15 · I18
5

Configuration as data: YAML, 25 numbered rules, validate and try modes; routes supervised.

Carries operations editing and verifying without a build, and one dead route never taking the pod with it.

spec D29 · D30 · D31 · D35 · I14 · I21

Deliberately not here: a second replica, an expression language, an attempt-history table, multiple targets per route, creation of buckets or tables, a Quarkus scheduler. Each has a named seam or a recorded reason in spec sections 15 and 16. The spec wins wherever this page and it disagree.
