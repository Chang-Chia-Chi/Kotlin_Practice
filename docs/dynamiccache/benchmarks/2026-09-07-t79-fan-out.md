# T79 before and after: fan-out runs the partition groups concurrently

**Date:** 2026-09-07. **Machine:** the same Windows 11 host as the T47 and T77 passes.
**Before:** `ca75415f` (the P7 plan commit, T79's base). **After:** `f39f1dd0` (T79's code).
Nothing else is in either tree: `misc/ai_gen` was not merged before the after pass, so the two
trees differ only by T79's own change.

**Instrument:** `DynaCache/bench/single-node.sh`, taken from branch `t77` as a file (not a
merge) and extended with the `fanout` pass group described below.
sha256 `78d9f969e07dda9c27ab45f88658bc4b503438d1371fe3f565c7aadfa62c618c`, identical bytes for
every pass here. Invoked as
`QUIET_BUDGET=20 MGET_KEYS="2 8 16 64" SECTIONS=dynacache PASSES=fanout bash ...`,
`-c 50 -n 100000 -r 100000`, node at 16 partitions under fsync `NEVER`, redis:7
`sha256:71da9275...` as the reference. Two samples per side, reported separately, because the
deltas needed a noise band to be read against.

## What the ticket asked for and what the tool can do

The ticket asks for `-r 100000 -t mset,mget`. `redis-benchmark` has no `mget` test, and an
arbitrary command supplied on the command line **replaces** `-t` rather than joining it, so
that flag combination cannot be run. The write side here is `-t mset`, which is
redis-benchmark's own ten-key MSET. The read side is an arbitrary `MGET` command with K copies
of `key:__rand_int__`, which is also the only way to vary the key count. Both run under
`-r 100000`; without it every key of a multi-key command is the same key, one partition serves
the whole command and the fan-out is never exercised at all.

## Load at each pass

Every pass on both sides recorded `quiet=NO_TAKEN_UNDER_CONTENTION`: one foreign idle
`java.exe` (about 73 MB, another session's) was present throughout and the gate requires none.
CPU idle was 85 to 94 percent at every pass, so the contention was a process count and not real
CPU competition, and it was the same on both sides.

## Findings

**1. Pipelined MSET is 2.17 times faster, and that is the whole of the measured gain.**
31845 to 69134 requests per second, with a run-to-run spread of 6 to 10 percent on that pass, so
the change is roughly twenty times the noise. p50 falls from 10.73 to 6.89 ms and p99 from 35.04
to 22.84 ms. Against redis:7 the node goes from 30 to 65 percent of Redis's pipelined MSET rate,
and its own pipelining gain (P16 over plain) rises from about 1.9x to about 4.4x, next to
Redis's 4.8x. This is anomaly 4's number and it is answered.

**2. MGET shows no change this machine can measure, at any key count.** Every ratio falls
between 0.95 and 1.10 while the run-to-run spread on the same passes runs from 1 to 32 percent.
Recorded as within the noise: the sweep neither confirms nor denies a gain on the read side.

**3. MSET plain is 0.93, against a spread of 18 to 21 percent on that pass.** Within the noise
and recorded as such. It is not evidence of a regression, and it is not evidence of its absence.

**4. The change lands on finding 1 alone.** The ticket's rule is that a gain under the noise
lands nothing; the pipelined MSET gain is far over it, so the code stands on that pass and the
MGET passes are recorded as inconclusive rather than as support.

**Hypothesis, not measured here, for why the write side moved and the read side did not.** A
fanned write appends to the WAL per group and its reply waits for that entry (C14), so the old
chain serialized the log work as well as the executor hops, and running the groups together
lets one batch cover all of them. A fanned read has no log at all: plain MGET is bound by the
round trip (every key count sits near 20000 rps with 50 clients) and pipelined MGET is bound by
CPU, so neither exposed the serial hop. Separating the log's share from the executor's is
T78's pass, not this one.

**5. No sign of the queue-depth problem the plan entry asks about.** Under `-P 16` the after
side's p99 does not grow against the before side at any key count: 6.80 against 9.07 at two
keys, 11.35 against 15.29 at eight, 14.69 against 14.00 at sixteen, 23.67 against 24.94 at
sixty-four. Concurrent submission did not make the tail worse, so the bounded-queue ticket the
plan entry conditions on this pass is not triggered. That is a single-client-shape result; it
says nothing about a thousand-key command, which the progress entry flags separately for the
router.

**6. At 64 keys pipelined the node is faster than redis:7, 42347 against 31133.** Not an
incidental: 64 keys is where the old sequential chain cost the most, up to 64 executor hops in a
row for one command, so it is the point where removing the chain should show hardest. It does.
Redis's own multi-key path degrades faster with key count than DynaCache's does once the groups
run together.

## Instrument change

`DynaCache/bench/single-node.sh` gains, in T77's style and with every existing default
unchanged:

- `MGET_KEYS` (default `2 8 16 64`), the key counts the sweep walks.
- `COMMAND`, one arbitrary command for `pass` to run instead of the `-t` list. It is placed
  last on the redis-benchmark line, because redis-benchmark reads every word after a command as
  that command's argument and silently swallows a flag put behind it.
- `fanout_passes`, selected by `PASSES=fanout` and **off by default**: it is one ticket's
  measurement, not part of what a release run takes. MSET runs before the sweep so the reads
  find keys that are there.
