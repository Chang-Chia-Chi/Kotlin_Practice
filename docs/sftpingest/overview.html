SFTP Ingest, Drawn

Every hour: take every finished file out of one SFTP folder, copy it into MinIO, move the original to a temp folder, and tell downstream. The whole design exists to make one sentence true: a file can be lost only if Oracle, MinIO and the SFTP server all lose it at once.

Part 1

The job, as a mailroom

A courier checks an inbox once an hour. For every envelope it finds, it copies the envelope into a vault and checks the copy, stamps the original and moves it to a "done" tray, then tells everyone who cares that the copy is in the vault. The whole time it writes each step into a logbook.

The three promises

Nothing is lost

A file leaves the inbox only after its copy is verified in the vault. The move is the last thing ever done to the original, so a crash before it leaves the file where it was, to be redone.

Nobody is told too early

"Moved" and "tell downstream" are written into the logbook in one stroke. A separate loop sends the notifications, so one can only ever go out after the copy exists and the original is moved.

One bad file never stops the rest

Every file is handled on its own. A file that fails five times, or fails the quality check, is marked, left in the inbox and handed to an operator. Nothing is ever deleted.

Part 2

Three pieces of state, three owners

Everything not drawn below is stateless and can be killed at any moment. The connector remembers only which files it has emitted and not yet heard back about. The ledger is the single source of truth for what happened to a file. The relay's set is a "these rows are taken" guard, not a cache and not a store.

One file's journey, and where a crash lands

One coroutine per file, at most four at a time. The ack is the commit point for the source: it is the last write to the original and it happens only after the copy is verified. Everything after it is made reliable by the outbox, not by ordering.

The ledger, as it looks for one file

file_transfer id 4471 vendor-drop /inbox/orders-0903.csv 9,812,404 B 2026-09-03T07:41:09Z SEEN → DOWNLOADED (sha256 3f9c…e2a1) → UPLOADED (landing/vendor/orders-0903.csv, v 7Kq…) → ACKED → DONE delivery_outbox for 4471 downstream DELIVERED attempts 1 reference req-8c21f audit-topic PENDING attempts 3 next 07:53:40 last HTTP 503

Two tables because one file has many deliveries and each needs its own attempts, retry time and reference. No attempt-history table: every attempt logs its file id, channel, attempt number, status and reference, and that is the trace.

The second loop: the relay

A cold Flow over the ledger with a bounded buffer and parallel workers, woken by every ack and by a 30-second sweep. Not a SharedFlow: a shared flow broadcasts to every subscriber, drops values when nobody is collecting, and never completes. Each of those is wrong for a work queue where one worker must handle each row and none may be lost.

Part 3

The five decisions that carry the requirements

Ranked. If you read nothing else in the spec, read these entries in its decision log.

1

The ledger is the only truth; the connector persists nothing.

Carries "no data lost": every file has a durable resume point, and after any crash the next poll continues from it instead of guessing. The connector's own dedup store is deliberately unused, because a file recorded as uploaded but not yet moved would be filtered out and never acked.

spec D1 · 4.3 · 4.4
2

Ack is the commit; deliveries are created in the ACKED transaction; reconciliation repairs move-then-crash.

Carries "nobody is told too early": the notification becomes durable in the same instant the source is committed, and a separate loop sends it. The one crash window this leaves, between the move and the ledger write, is closed at the next poll by noticing the file is gone.

spec D6 · 4.5 · I10 · I11
3

Deterministic object key; prune every other version after every PUT.

Carries "delete the old version if we upload twice" on a bucket whose versioning cannot be turned off. A retry is an overwrite, never a sibling, and the prune after the retry also removes a version left by an earlier crash.

spec D5 · 6.3 · I6
4

Cold-flow relay with a bounded buffer and an in-memory guard; per-channel policy; a failed delivery never fails the file.

Carries "high performance" and "multiple channels": memory is bounded by construction, one slow channel never blocks another, and a dead downstream becomes a dead-letter with a re-drive button instead of a stuck pipeline.

spec D7 · D9 · 7.3 · 7.4 · I4 · I5 · I13
5

Every timeout below the drain; bounded parallelism everywhere; one replica.

Carries "high stability": a pod can be restarted at any moment and converges, shutdown is bounded, and the server's five-session cap is respected as a real ceiling of about four parallel transfers.
